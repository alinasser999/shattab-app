## حدود التصميم

- Flutter (إطار تطبيق الموبايل) ولوحة Next.js (إطار واجهات الويب) هيبقوا عملاء للـ API (واجهة خدمات موحدة)، ومش هيتصلوا مباشرة بقاعدة البيانات.
- OpenAPI (صيغة معيارية لوصف المسارات والطلبات والاستجابات) بالإصدار 3.1 هو العقد المقترح تحت /api/v1. كل عملية ظاهرة لها operationId (اسم فريد للعملية)، وsecurity (قاعدة المصادقة المطلوبة لكل عملية)، وx-contract-status (تصنيف يوضح هل العملية أساس محلي موجود أو هدف مخطط).
- Fastify (إطار خفيف لخدمة Node.js) modular monolith (تطبيق واحد مقسوم لوحدات واضحة) هو هدف التنفيذ، مش دليل على وجود مسارات أعمال حاليًا.
- PostgreSQL (قاعدة البيانات العلائقية) هتفضل داخل الشبكة الخاصة. RLS (سياسات قاعدة البيانات اللي بتحدد الصفوف المسموح لكل مستخدم يشوفها أو يعدلها) طبقة دفاع إضافية مع صلاحيات الـ API.
- Cognito (خدمة مُدارة لهوية المستخدمين) هو هدف تسجيل الدخول للمستخدمين؛ إعداد المزود أو رسائل مصر مش متحققين هنا. مسارات كلمة السر وOTP وتسجيل الدخول الاجتماعي تفضل ضمن تدفقات المزود، مش مسارات API تخترع بديلًا.
- R2 (تخزين ملفات Cloudflare) هدف للوسائط العامة المعتمدة، وOCI Object Storage (تخزين الملفات في Oracle Cloud) هدف للوسائط الخاصة. FCM (إشعارات Google لتطبيقات الموبايل) وAPNs (إشعارات Apple) يفضلوا مزودي الإشعارات.
- الـ API هي المصدر الموثوق للصلاحيات وانتقالات الحالة؛ الواجهة بتتحكم في العرض والتنقل بس.

## قواعد مشتركة لكل العمليات

### الهوية والصلاحيات

- `ConsumerBearerAuth` (مصادقة المستخدم برمز دخول) مخصص لحسابات المستهلكين، و`AdminBearerAuth` (مصادقة منفصلة للمشغّل) للإدارة. كل عملية تصرح بمتطلب المصادقة؛ العملية العامة فقط تستخدم security فارغة.
- Cognito مزود مستهدف، مش مزود التطبيق الحالي. الخادم الموثوق يتحقق من توقيع الرمز ومصدره وجمهوره/العميل وصلاحيته ونوع استخدامه، وبعدها يربط `sub` الموثق بهوية Shattab داخلية واحدة.
- ممنوع الثقة في `userId` أو `role` أو علامة الإدارة اللي يرسلها العميل، وممنوع الربط التلقائي للحسابات القديمة برقم الهاتف أو البريد. أي تعارض أو تكرار يوقف العملية لحد مصالحة يدوية.
- عند تنفيذ PostgreSQL، سياق الهوية الداخلية يتضبط داخل المعاملة بعد التحقق فقط، ويتعمل rollback (إلغاء تغييرات المعاملة) لو إعداد الهوية أو الطلب فشل. دور تشغيل قاعدة البيانات محدود، مش مالك الجداول المحمية ومش مسموح له يتجاوز `RLS`؛ كده سياسات قاعدة البيانات تفضل طبقة دفاع إضافية وهوية الطلب ما تتسربش لاتصال يعاد استخدامه.
- صلاحيات الإدارة مستقلة عن دور صاحب المنزل أو المقاول. `request_media.review` لازم تتمنح يدويًا وتفضل لحد سحبها يدويًا؛ صلاحية admin العادية وحدها ما تكفيش. افتراض إن دور `owner` الإداري وحده يمنح/يسحبها ومن غير self-grant غير معتمد من المستخدم ومش تطبيق حالي. ما فيش endpoint للمنح أو السحب في العقد، ومراجعة الصور تفضل مقفولة لحد اعتماد الجهة والإجراء وسجل التدقيق.

### الطلبات، الصفحات، وإعادة المحاولة

- DTO (شكل بيانات محدد للطلب أو الاستجابة) لكل عملية موصوف في OpenAPI. المخططات تقبل الحقول اللي اتحددت فقط في الكائنات المقفولة؛ ما نضيفش حقولًا من غير قرار أو دليل مصدر.
- limit (عدد عناصر الصفحة) الافتراضي 20، والحد من 1 إلى 50. cursor (مؤشر معتم للمتابعة) مربوط بالترتيب والفلاتر، وبهوية المستخدم للقوائم الخاصة؛ العميل ما يكوّنش قيمته بنفسه.
- Idempotency-Key (مفتاح يمنع تكرار أثر العملية عند إعادة إرسال نفس الطلب بعد انقطاع الشبكة) مطلوب في عمليات الإنشاء والانتقال الحساسة اللي بتحدده. المفتاح مربوط بهوية موثقة والعملية/المورد وبصمة المحتوى؛ نفس المفتاح والمحتوى يعيد النتيجة الأصلية، واستخدامه لمحتوى مختلف يرجع IDEMPOTENCY_KEY_REUSED. مدة الاحتفاظ بالمفتاح مش محددة في العقد.
- GET للقراءة، وعمليات PUT/DELETE المتكررة مصممة كإضافة/إزالة قابلة للتكرار، أما الانتقالات الحساسة فتستخدم Idempotency-Key. الخادم هو اللي يحدد الحالات والتوقيتات.
- الأخطاء ترجع application/problem+json (صيغة مشكلة معيارية) وبها code ثابت وrequestId، وممكن fieldErrors للحقول. العميل يعرض ترجمة عربية حسب code بدل نص إنجليزي خام.
- الأكواد العامة تشمل AUTHENTICATION_REQUIRED وINVALID_TOKEN وFORBIDDEN وNOT_FOUND وVALIDATION_FAILED وSTATE_CONFLICT وIDEMPOTENCY_KEY_REUSED وACCOUNT_LINK_REQUIRED وNOT_ELIGIBLE وQUOTA_EXCEEDED وRATE_LIMITED وDEPENDENCY_UNAVAILABLE وINTERNAL_ERROR. ده قاموس العقد؛ التطبيق الفعلي محتاج يوحّد استخدامه.
- مفيش حد أقصى مثبت لطول تعليق التقييم أو أسباب وملحوظات قرارات الإدارة. العمليات تفضل خلف بوابتي `review-comment-length-policy-reconciliation` و`admin-reason-length-policy-reconciliation` لحد مراجعة سياسة المنتج والمصدر. حدود معدل الطلبات، مدة الاحتفاظ بمفاتيح منع التكرار، وأحجام ملفات الميديا برضه مش محسومة إلا لو YAML بيحدد قيمة صريحة.

### حدود أطوال النصوص المؤجلة

الأرقام `400` و`2000` اتشالت من OpenAPI لعدم وجود دليل مصدر موثق يثبتها؛ العقد ما بيقفلش حدًا بديلًا. بوابة `review-comment-length-policy-reconciliation` مطلوبة لحقول التعليق في إنشاء التقييم (`BriefReviewInput.comment` و`ContactReviewInput.comment`). بوابة `admin-reason-length-policy-reconciliation` مطلوبة لسبب إيقاف المستخدم، وملاحظات قرار البلاغ، وسبب رفض التحقق، وسبب رفض الدفع. فضلت الدلالات الوظيفية زي ما هي: سبب إيقاف المستخدم غير فارغ ومطلوب؛ قرار إزالة/إيقاف صاحب البلاغ يحتاج note غير فارغ بينما dismiss ممكن من غيره؛ ورفض التحقق أو الدفع يحتاج سبب غير فارغ. المطلوب قبل تفعيل المسارات هو حسم الحد الأقصى ومصدره؛ مفيش حد نصي مُخترع في المخطط.

### الخصوصية والتخزين

- بروفايل المقاول العام ما يرجعش رقم الهاتف؛ الرقم يظهر فقط في استجابة handoff المصرح بها، مش في البحث أو البروفايل أو المنشور.
- الاستجابات الخاصة والمراجع والبايتات الخاصة ووجهة الاتصال تستخدم `Cache-Control: no-store` (توجيه يمنع المتصفح والوسيط من حفظ الاستجابة). في قائمة مراجع صور الطلب، الترويسة إلزامية وقيمتها محصورة في `no-store`. ده تحكم في طبقة HTTP فقط، ومش بيمسح ذاكرة صور التطبيق المؤقتة. ما فيش URL عام أو signed URL (رابط مؤقت يحمل صلاحية وصول) للصور الخاصة؛ `mediaId` (مرجع ملف معتم) لوحده مش تصريح وصول.
- في صور الطلب الخاصة، Flutter لازم يتجنب shared image cache (ذاكرة الصور المشتركة) في البداية؛ أو يعزل التخزين المؤقت بمفتاح فيه هوية المستخدم/الجلسة وإصدار الصورة، ويمسحه عند sign-out (تسجيل الخروج) أو account switch (تغيير الحساب). قاعدة no-store تفضل طبقة حماية إضافية.
- كل قراءة لمرجع أو محتوى صورة خاصة تعيد فحص العلاقة والصلاحية الحالية. API يمرر البايتات بعد الفحص بدل redirect لرابط تخزين قابل لإعادة الاستخدام.
- سجل الإشعار والبيانات الخاصة ما يرجعوش روابط/وجهات اعتباطية قابلة للتنفيذ.
- ما فيش اتصال قاعدة بيانات مباشر من Flutter أو المتصفح، ولا خدمة قاعدة بيانات منشورة على الإنترنت ضمن هذا العقد.

## قرارات المنتج والأمان المثبتة في العقد

### اتصال واتساب والمكالمة

- رقم الهاتف ما يظهرش كنص في البروفايل أو المنشور. التواصل بزر اتصال أو WhatsApp خارجي؛ مفيش دردشة داخل شطب.
- أي حساب مسجل ومكتمل التهيئة — صاحب منزل أو مقاول — يقدر يتواصل مع مقاول تاني. الضيف لما يضغط يتحول للتسجيل/الدخول. بعد نجاح المصادقة والتهيئة يرجع لنفس صفحة البروفايل أو المنشور، ويضغط الزر تاني بنفسه؛ التطبيق ما يفتحش تطبيق خارجي تلقائيًا.
- `POST /contact-handoffs` يسجل نية مستخدم مصادق ويرجع وجهة إطلاق قصيرة الصلاحية في الاستجابة الخاصة فقط مع `Cache-Control: no-store`. ضغطة الزائر لا تتحول لحدث API؛ لازم يرجع ويعيد الضغط بعد التسجيل.
- `POST /contact-handoffs/{handoffId}/accepted` يسجل فقط إن التطبيق أفاد بأن نظام التشغيل قبل طلب فتح الوجهة. ده لا يثبت إن مكالمة اتصلت أو رسالة اتبعتت أو محادثة بدأت أو الطرف التاني رد. إعادة الطلب بنفس idempotency key ما تعملش حدث قياس مكرر.
- المسموح للقياس: قناة التواصل (`call` أو `whatsapp`)، مصدر الزر (`profile` أو `post`)، ونتيجة handoff المرصودة. ممنوع تسجيل رقم الهاتف أو الاسم أو البريد أو نص الرسالة أو launch URI أو الموقع أو معرّف المقاول المستهدف في التحليلات أو السجلات المعتادة. الاحتفاظ بحدث القياس وربطه بهوية داخلية ما زال غير محسوم؛ ما نحددش مدة أو جمهور وصول من غير قرار.

### صور طلبات التشطيب

- `POST /me/request-media` بيرجع `StagedMediaEnvelope` فيه مرجع الصورة الخاصة المرحلي (`mediaId`) من غير رابط تخزين. استجابة `201` اللي فيها المعرّف عليها `Cache-Control` إلزامي بقيمة `no-store` عشان HTTP cache (ذاكرة تخزين مؤقتة للطلبات) ما يحتفظش بالرد.
- **العقد المستهدف:** صور الطلب يقرأها صاحب الطلب والمقاول صاحب العرض المقبول فقط، وطول ما الطلب نشط. قبل قبول عرض المقاول وبعد اكتمال الطلب أو إلغائه، الوصول مرفوض. أهلية المقاول لرؤية فرصة مفتوحة مش كفاية. الخادم يعيد فحص العلاقة والحالة عند جلب المراجع وعند جلب كل صورة؛ `mediaId` مش تصريح وصول.
- غياب أو فساد `bearer token` (رمز وصول يحمله الطلب لإثبات الهوية) يرجع نفس `401` الموحد قبل أي بحث عن الطلب أو الصورة، بصرف النظر عن وجودها. على مسارات المستخدمين، بعد نجاح المصادقة، أي مستخدم لا يملك العلاقة المطلوبة، أو طلب/صورة غير موجودة، أو طلب مكتمل/ملغي/غير نشط، يحصل على نفس `404 Problem` (استجابة خطأ موحدة) بكود `NOT_FOUND` ومن غير تفاصيل تفرق الحالات. مفيش عدد ولا `hasMedia` ولا URL ولا إشارة تكشف وجود الملف. الـ API يبث الصورة الخاصة من خلال اتصال مصادق عليه ويرجع `Cache-Control: no-store`؛ ما يعملش redirect إلى رابط تخزين دائم أو رابط موقّع قابل لإعادة الاستخدام.
- حساب الإدارة ما يرثش الوصول من كونه إداريًا. لازم منحه يدويًا `request_media.review` لغرض شكوى أو إشراف؛ المنح يفضل فعال لحد سحبه يدويًا. بعد مصادقة صحيحة، الخادم يفحص الصلاحية ويسجل كل محاولة، بما فيها الرفض، قبل أي استعلام يكشف وجود الطلب أو الصورة. لو الصلاحية مفقودة، يسجل الرفض بشكل دائم بالمعرّف المرسل قبل بحث المورد، ثم يرجع نفس `404 Problem` بكود `NOT_FOUND` المستخدم للمورد المفقود. فشل نظام فحص الصلاحية أو سجل التدقيق يرجع `503` عامًا ويمنع البحث عن المورد. الأدمن الممنوحة له الصلاحية يقدر يراجع الصور المحتفَظ بيها للشكاوى أو الإشراف حتى بعد اكتمال الطلب أو إلغائه؛ إغلاق الطلب وحده ما يمنعش المراجعة. في الوصول المسموح، يعيد الخادم فحص علاقة الصورة بالطلب ويسجل المشاهدة قبل إرجاع المراجع أو البايتات. سياسة مدة الاحتفاظ بالصور وحذفها بعد الإغلاق لسه غير محسومة؛ ما نفترضش مدة أو حذف تلقائي قبل اعتمادها. مفيش شرط `case ID`.
- الجهة اللي تمنح/تسحب الصلاحية لسه غير محددة. استخدام دور `owner` وحده كجهة منح/سحب هو افتراض غير معتمد، مش صلاحية قائمة أو قرار من المستخدم. ممنوع إنشاء self-grant أو مسار API للمنح في هذا العقد.
- **الحالة المحلية والحيّة لا تحقق العقد:** المصدر المحلي يضبط `brief-photos` كحاوية عامة وسياسة المجلد فيه للمالك فقط؛ التحقق من الصور أثناء الرفع لا يجعل القراءة خاصة. اللقطة الحية في 2026-10-26 وجدت الحاوية العامة وبها 4 كائنات. ده hard blocker لنقل الصور الخاصة أو القطع للإنتاج. لم تُقرأ أسماء الملفات أو محتوياتها، ولم تتغير إعدادات الحاوية.
- قبل التحويل لازم خطة منفصلة معتمدة ومجربة لنقل الملفات، وإيقاف الروابط العامة القديمة، وتقاعد نسخ التطبيق التي تعتمد عليها، ومراجعة نسخ الكاش العامة، وعزل كاش الصور الخاصة بهوية/جلسة وإصدار الملف، ومسحه عند تسجيل الخروج أو تبديل الحساب. `no-store` وحده لا يمسح كاش التطبيق.

## العمليات والحقول المؤجلة

العناصر دي غير موجودة كعمليات قابلة للاستدعاء تحت paths. بوابة القرار لازم تتقفل قبل إضافة أي عقد لها:

| العملية المؤجلة | بوابة الإغلاق |
|---|---|
| DELETE /me | سياسة الاحتفاظ وإعادة التحقق وحذف مزود الهوية والملفات والأجهزة والتعافي. |
| GET /me/entitlements | توحيد شروط الاشتراك ومفردات الاستحقاق المملوكة للخادم. |
| GET /me/notification-stream | تحديد النقل والرسائل والمؤشر والاستئناف والانقطاع وإعادة الاتصال. |
| GET /me/saved-portfolio-items | تأكيد واجهة قائمة المحفوظات وعقد القراءة. المصدر المحلي يثبت حفظ/إزالة وقراءة حالة عنصر واحد من شاشة التفاصيل، مش قائمة محفوظات للمحفظة. نفس gate المسماة saved-portfolio-route-parity في عمليات PUT و DELETE. |
| GET /billing/plans و POST /me/payment-requests | حسم اشتراكات المقاولين ومصدر الاستحقاقات ومزود الدفع والتحقق من الدفع/الـ webhook والتوافق مع المشتركين الحاليين. سجل طلبات الدفع الحالي لا يثبت عقد فوترة أو اشتراك. |
| POST /community/reports | حسم أنواع المحتوى المبلغ عنه وقائمة الأسباب وحدود الإدخال. |
| POST /requests/{requestId}/contact-handoffs | حسم سياسة تواصل المقاول مع صاحب المنزل والاستحقاق والعلاقة المطلوبة. |
| PATCH /reviews/{reviewId} | حسم هل التقييم قابل للتعديل وشروط ذلك. |

حقول مؤجلة: كتابة صورة الحساب avatarMediaId؛ فلاتر وترتيب بحث المقاولين؛ البحث وفلاتر المجتمع؛ رفع ميديا عامة لمنشورات المستخدمين. لازم مسار اعتماد وفحص/إعادة معالجة قبل إتاحة أي ملف عام.

فجوات محلية مرصودة لكنها مش موجودة في مصفوفة المسارات المعتمدة: تحديث تفاصيل بروفايل صاحب المنزل؛ كتابة بروفايل المقاول وأقسام الظهور؛ إنشاء/تعديل/حذف عناصر معرض المقاول؛ عقد API لقراءة حالة حفظ عنصر محفظة واحد؛ إجراء تسجيل إن الطرفين ما اشتغلوش مع بعض في متابعة التواصل؛ إجراءات الإدارة المباشرة لتغيير الخطة، وتغيير حالة التحقق، وحذف منشور.

ممنوع نخترع لهذه الفجوات مسارات أو أسماء حقول أو صلاحيات. أثرها: الـ 87 عملية تغطي المصفوفة الجاهزة بعد تأجيل قائمة المحفظة، ومش عقد كامل لكل شاشات التطبيق أو بديلًا كاملاً لـ Supabase. محتاجة planner follow-up يراجع سلوكها وأصحاب الصلاحية قبل توسعة OpenAPI.

## فجوات التنفيذ قبل النقل

1. **مصدر البيانات:** صالح اختلاف سجل الترحيلات والمخطط والدوال والسياسات والصلاحيات الحية والمحلية مقابل مرجع موثوق ومراجَع. اختلاف الأسماء والإصدارات مش تصريح بإعادة تشغيل جماعية للترحيلات المحلية.
2. **هوية الحساب:** حسم ربط Cognito sub بمعرّف Shattab الداخلي، ومعالجة التعارضات يدويًا، ومنع الربط التلقائي بالهاتف أو البريد؛ واختبار الحسابات الحالية واستعادة الحساب.
3. **صلاحيات الصور:** تجهيز خطة منفصلة ومعتمدة ومجربة لتغيير إتاحة brief-photos العامة ونقل الملفات وبيانات ربطها بالطلبات. تشمل الخطة الروابط العامة القديمة، نسخ الكاش العامة، وإخلاء أو عزل كاش Flutter ومسحه عند sign-out أو تبديل الحساب. ما نغيرش bucket حي كجزء من توثيق العقد.
4. **مراجعة الإدارة:** اعتماد الجهة التي تمنح وتسحب request_media.review، وتنفيذ منح يدوي دائم حتى السحب، وسجل وصول غير قابل للتعديل العادي؛ كل قراءة ومحاولة إدارية تتسجل قبل إرجاع أي بيانات، والفشل يمنع القراءة.
5. **توافق العملاء والخدمات:** راجع كل نسخ التطبيق التي ما زالت تتصل بـ Supabase مباشرة، ونقل/تقاعد روابط الصور العامة، وراجع أجسام Edge Functions وصلاحياتها، وتوافق الإشعارات والفوترة/الاستحقاقات. سجل طلبات الدفع لا يعني تلقائيًا وجود اشتراك أو استحقاق.
6. **تشغيل قاعدة البيانات:** شغّل الترحيلات على بيئة منفصلة بعد المصالحة فقط، ثم اختبر الصلاحيات لكل علاقة ودور، واختبر نسخًا احتياطية واستعادة فعلية قبل أي قطع.
7. راجع حدود الملفات ومعدلات الطلب ورسائل SMS ومكان التخزين والتكلفة من المزود والمصدر الحالي قبل اعتمادها.

## بوابات النشر والرجوع

- لا تنشر API أو قاعدة بيانات أو تغير DNS/Firewall أو إعدادات OCI/AWS/Cloudflare بموجب هذا المستند.
- قبل نقل إنتاجي: نسخة احتياطية مستعادة بنجاح في بيئة منفصلة، مطابقة بيانات وميديا، نجاح الدخول والطلب والعرض والقبول والاتصال والتقييم والإشعارات ولوحة الإدارة، واختبارات منع الوصول لمستخدم آخر.
- تحوّل مصدر الكتابة مرة واحدة بعد اعتماد خطة الرجوع. بعد أول كتابة على قاعدة الإنتاج الجديدة، الرجوع لقاعدة Supabase القديمة ممكن يفقد تغييرات؛ الأفضل إصلاح للأمام أو استعادة النسخة الجديدة، مع تسوية الكتابات.
- إيقاف Supabase مؤجل لحد اعتماد تبني إصدارات العملاء، تكافؤ الهوية والبيانات والميديا والإدارة والإشعارات، واختبار الاستعادة والرجوع.
- ما فيش وعد بتوفر 100% من سيرفر واحد أو بأعداد مستخدمين؛ لازم قياس فعل واختبارات حمل وخطة تعافي.
